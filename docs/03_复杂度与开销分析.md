# PeakAware 复杂度、工程风险与降级路线

## 1. 总结

工程风险较高的主要原因不是图捕获，而是必须同时保证：

- 所有通过 legality、closure 和结构验证的 SAVE 集合可合法 partition；
- 静态峰值能代表编译后的物理峰值；
- 搜索在大图上可扩展；
- 真实模型存在足够 activation 优化空间；
- PyTorch 内部 API 变化不会破坏系统。

因此采用一次捕获、分层搜索、插件隔离、Top-K 编译和明确回退，而不追求第一版全局最优。

## 2. 符号

- `V/E`：joint graph 节点和边；
- `A`：候选 SAVE value 数量；
- `R`：region 数量；
- `S`：seed 数量；
- `I`：repair/local-search 迭代数；
- `K`：进入真实编译的候选数；
- `Q`：Profiling DB 记录数。
- `L`：启用的反事实诊断层数，D0--D5 最多为 6。

## 3. 各阶段复杂度

| 阶段 | 典型复杂度 | 说明 |
|---|---:|---|
| Joint capture | 框架相关 | 只执行一次 |
| IR/alias/liveness 构建 | `O(V+E)` | storage union/find 可近线性 |
| Fixed frontier | `O(P+V)` | `P` 为参数数量或 parameter groups |
| 候选生成 | `O(V+E)` | region 发现可能需多次图遍历 |
| 单个闭包 | `O(V+E)` 最坏 | 使用 bitset/cache 降低重复成本 |
| 单个峰值仿真 | `O(V+E)` | 固定派生顺序 |
| 单个 D0--D3 静态诊断 | `O(L(V+E))` | `L <= 4` |
| D4 compiler 诊断 | `K * compile_cost` | 只用于 Top-K |
| D5 runtime 诊断 | `K * runtime_cost` | 只用于已实测候选 |
| Min-cut seed | 多项式 | 取决于 flow 实现和图规模 |
| Repair/local search | `O(I(V+E))` 最坏 | 增量事件和闭包缓存可降低 |
| Pareto pruning | `O(N log N)` | 二维 peak/time 可排序扫描 |
| Top-K compile | `K * compile_cost` | 最昂贵阶段，严格限制 K |

直接枚举所有 SAVE 集合为 `O(2^A)`，不可行。任意 backward schedule 搜索还会引入拓扑排序
组合爆炸，因此第一版不将其作为独立变量。

## 4. 降低搜索开销

### 4.1 Region 粗化

先以 block/residual/attention region 为变量，峰值附近再展开 value。目标是使大模型初始变量
从数千个 value 降到几十或几百个 region boundary。

### 4.2 闭包缓存

缓存：

- value 到最近 mandatory/saved ancestor；
- region 内局部闭包；
- plan bitset hash 到 `RecomputeClosure`；
- shared ancestor 的引用计数。

### 4.3 增量仿真

单个 SAVE/DROP move 只影响相关 ancestor、consumer 和 live interval。第一版可使用完整扫描
保证正确，验证后再加入增量更新。

### 4.4 候选限额

默认配置建议：

```text
lambda_trials: 8--16
repair_iterations: 16--32
plans_per_peak_bucket: 2--4
compile_top_k: 3--5
runtime_validate_k: 2--3
```

## 5. Cost 查询开销

ProfileDB 以规范化 signature hash 建索引，精确查询接近 `O(1)`。邻近 shape 查询不应扫描
全部 `Q`，需要按 op、dtype、layout、hardware 建复合索引，再对小候选集合计算距离。

Profiling 采集不在每次搜索中全量执行：

1. 优先复用数据库；
2. 缺失值使用解析/fallback cost；
3. 只为热点或低置信度算子补 profile；
4. Top-K 端到端测量用于校准，而非逐候选逐算子 profile。

## 6. CPU、GPU 与磁盘开销

### CPU 主存

主要来自 FX graph、FakeTensor metadata、ShapeEnv、IR、bitset、event streams 和 profile index。
IR 中不要保存重复 FakeTensor 对象；shape/dtype/stride 应规范化并 intern。

### GPU

搜索阶段不执行真实张量。GPU 仅用于 profile collection 和候选验证。M0/M1 候选在同一进程串行
执行，但每次必须恢复 model/optimizer/RNG/allocator measurement state；M2 使用隔离 worker，避免
allocator cache 和残留编译状态污染结果。

### 磁盘

保存：SQLite/Parquet profile DB、plan JSON、测量 CSV/JSON 和必要 trace。Inductor cache、
Nsight trace 和大模型图应设置清理策略，不默认提交版本库。

## 7. 主要工程风险

### R1：PyTorch 内部 API 不稳定

风险：AOT partitioner、Inductor scheduler 和内部函数签名随版本变化。

措施：

- 所有内部访问集中在版本适配插件；
- `patch_method` 声明版本范围并校验签名；
- CI 固定主支持版本，其他版本 fail closed；
- 核心 IR/search 不导入私有 PyTorch 模块。

### R2：任意 SAVE 集合无法下发

风险：RNG、mutation、alias、tangent 和 output ordering 导致图不合法。

措施：先支持纯函数、固定 shape、单设备模型；legality pass 保守强制 SAVE；每个 plan 先做结构
验证，再运行数值验证。

### R3：静态峰值与物理峰值偏差

风险：fusion、buffer reuse、workspace、allocator fragmentation。

措施：报告逻辑峰值和校准峰值两层结果；ProfileDB 保存 workspace；Top-K 实测；使用安全裕量；
把误差作为论文指标，不隐藏失败候选。

### R4：真实模型缺少收益

风险：参数、梯度、optimizer 或 LM-head frontier 主导，activation plan 无法降低 overall peak。

措施：Fixed Frontier Analyzer 先判定 opportunity；主实验选择 activation-dominated shape；同时
报告无效配置，作为方法边界而非删除结果。

### R5：根因归因不唯一

风险：不同计划的峰值发生在不同 phase/op，简单组件差分会重复归因或给出错误因果结论。

措施：使用声明顺序的 D0--D5 反事实 ladder；同时展示 baseline/candidate 峰值快照；允许多个
root cause 和低 confidence；不把顺序相关分解声称为唯一数学因果分解。

### R6：搜索时间超过收益

风险：编译和 profiling 成本高于训练节省。

措施：M0/M1 使用一次捕获、内存 memoization、显式无收益 early-stop 和 Top-K 限额；M2 再加入
capture/analysis/executable 三层 cache 与 profile cache，并报告 amortization steps：

```text
amortization_steps = optimization_time
                   / (baseline_step_time - optimized_step_time)
```

### R7：插件和 patch 相互污染

风险：全局 monkey patch、重复包装、异常后未恢复和并发编译。

措施：插件优先；patch 只存在于 `PatchSession`；wrapper chain 有 owner/priority；异常时
`finally` 恢复；编译在独立进程中运行。

## 8. 降级路线

| 完整目标失败点 | 降级版本 |
|---|---|
| 任意 value partition 不稳定 | 只优化 region/block boundary |
| Inductor 静态校正不可得 | AOT liveness + 安全裕量 + Top-K 实测 |
| Costmodel 重写过慢 | Legacy adapter + ProfileDB + roofline fallback |
| 大图 min-cut/repair 过慢 | greedy peak-live-set repair |
| 全尺寸 LLaMA 无硬件 | FakeTensor 全图 + 缩小模型真实验证 |
| MoE routing 不稳定 | 固定 routing trace 或移出主实验 |
| throughput 优势不显著 | 聚焦预算满足率、峰值预测和无效搜索检测 |

## 9. 阶段 Go/No-Go

### Gate 1：捕获与 IR

通过条件：Tiny residual、ResNet block、Transformer block 均能 fake capture；alias 和
liveness 单测通过。失败则不开发搜索。

### Gate 2：任意 SAVE 闭环

通过条件：在第一版支持域内，至少十个手工 SAVE plan 可下发并与 baseline 梯度一致。支持域
限定为纯函数、固定 shape、单设备、受控 RNG，且不存在未建模 alias 或 mutation。失败则
降级到 region-only。

### Gate 3：机会验证

通过条件：至少三个真实模型/shape 存在可解释的 BW 或 overall peak 改善空间。失败则将论文
转向诊断工具。

### Gate 4：搜索收益

通过条件：诊断器能解释 min-cut 的期望收益差距，且 peak-aware greedy/min-cut repair 比
PyTorch min-cut 在相同实测峰值下更快，或显著降低预算违约率。失败则重新检查 candidate
space、root-cause evidence 和 peak model。

### Gate 5：论文闭环

通过条件：预测误差、吞吐、预算满足率、搜索开销和正确性均有完整数据；结果可由固定配置
和脚本复现。

## 10. 推荐开发模式

```text
M0 模式：Tiny residual + hand plans + aot_eager + full-step measurement
M1 模式：主模型小规格 + static/legacy cost + min-cut repair + Top-K
M2 模式：ProfileDB + D0--D5 + cache + isolated runtime
M3 模式：小图 exact solver、dynamic/microbatch/MoE 等独立扩展
```

任何时候都优先完成一个端到端闭环，而不是同时扩展模型、Costmodel、搜索和 compiler patch。
