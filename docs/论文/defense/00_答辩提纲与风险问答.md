# 答辩提纲与风险问答

本文档规定 15--20 分钟答辩的页序、演示策略和高风险问答。答辩中的最终数字只从
`evidence/00_论点证据账本.md` 读取，图只从 `figures/` 的冻结产物读取。任何 `planned`、`smoke`、
`provisional` 或 `invalid` 结果都不得在答辩中口头升级为已证实结论。

## 1. 答辩目标与一句话主线

答辩不是罗列模块，而是让评委记住一句话：

> 优化跨越 FW/BW 边界的 saved activation，并不足以保证完整训练 step 的物理峰值预算；PeakAware
> 通过 storage/phase/fixed/compiler-aware 诊断、SAVE repair 和可执行计划实测选择来闭合这条差距。

每页只承担一个论证动作。推荐总时长 18 分钟，预留 2 分钟给切换和意外；若现场严格限制 15 分钟，
删除第 5 页的展开推导和第 13 页的次要消融，不压缩核心证据页。

## 3. 每组页面的讲述脚本

### 3.1 第 1--4 页：先证明问题值得研究

推荐口头路径：

1. “激活重计算通常决定哪些 tensor 跨越 FW/BW 边界保存。”
2. “但用户真正遇到的 OOM 由完整 step 任一时刻的最大物理 live set 决定。”
3. “两者在一些 workload 上一致，在 alias、重计算波或 fixed frontier 主导时会分离。”
4. “所以本文不是否定 min-cut，而是补上其边界目标到 complete-step budget 之间的闭环。”

第 3 页必须使用当前代码、可辨认 runtime adoption、真实 baseline 的冻结案例。若 G-1/G-3/G-7 未通过，
改为讲机制复现与待验证假设，不声称真实模型普遍性。

### 3.2 第 5--9 页：每个组件都由问题推出

- fixed frontier 对应 feasibility analysis；
- storage alias 对应 storage-normalized IR；
- recompute transient/phase migration 对应 phase-aware live-set model；
- 静态排序误差对应 Pareto Top-K runtime correction；
- 计划标签可能与执行不一致，对应 plan identity、lowered runtime marker 和 correctness gate。

讲 D0--D5 时先给每层新增的信息，再给残差如何产生 hint。不要从类名、文件名或开发顺序开始。

### 3.3 第 10--13 页：先讲协议，再讲胜负

结果页前必须用一页交代公平性：

- 真实 AOT min-cut、block AC、SAC 与 PeakAware 的执行语义；
- ResNet-50、ViT-B/16、BERT-like-2L-64H、GPT2-like-2L-64H 的真实规格；
- 50/65/80/95/100% all-save measured peak 的相对预算；
- 相同 batch、dtype、optimizer、compile mode、warmup、repeats 和 correctness；
- measured allocated peak、steady-state throughput、failure/OOM/fallback 均进入结果。

主结果先回答预算满足，再回答 matched peak 下吞吐；预测精度和诊断准确率是机制证据，不能代替端到端
用户收益。跨 workload 的 speedup 使用既定统计口径，页面同时保留逐点分布。

### 3.4 第 14--15 页：主动讲边界

不要把负结果留给评委追问。明确说明：

- fixed/optimizer frontier 支配时，activation-only 方法可能没有峰值收益；
- hints 在某些真实候选空间可能不改变最终计划；
- raw cost ranking 弱时，Top-K 实测是必要成本；
- internal AOT ABI、单设备和静态 shape 限制外推；
- PeakAware 的“更优”只在已测工作负载、相同协议和 physical-peak 预算下成立。

结尾不说“全面优于”，而说“把优化目标和最终验收目标对齐，并明确何时 activation-only 优化不可行”。

## 4. 演示策略

### 4.1 推荐演示形式

优先使用 60--90 秒预录或离线回放，不在答辩现场重新编译四模型。现场只展示一个已经冻结的短流程：

1. 读取一个固定 workload 和预算；
2. 展示候选的 plan ID、seed/provenance 和 predicted phase peak；
3. 展示 selected plan 的 lowered runtime marker 与 correctness 状态；
4. 展示 FW/BW/optimizer measured peak、dominant phase 和预算是否满足；
5. 打开对应 manifest/checksum 或自动生成图，证明结果可追溯。

演示目的不是追求视觉效果，而是证明“计划确实执行、峰值确实测量、结果确实可追溯”。

### 4.2 演示前验收

- 演示输入、commit、环境和 artifact checksum 已冻结；
- 使用短路径，不依赖网络，不执行包安装；
- GPU 不可用时可以直接播放同一 run 的录屏和日志；
- 页面中隐藏无关 warning，但不隐藏 correctness、OOM、timeout 或 fallback；
- 预先验证终端字体、图中文字和 16:9 投影可读性；
- 准备一张静态后备页，包含与演示相同的 plan ID 和 measurement 字段。

### 4.3 不建议现场做的事

- 临时运行 Inductor cold compile；
- 从旧 artifact 中挑一个收益最大的点而不展示协议；
- 只显示计划名称，不显示 runtime adoption marker；
- 将合成 root-cause demo 说成真实模型诊断准确率；
- 现场修改预算以寻找“更好看”的结果。

## 5. 高风险问答

### Q1：min-cut 峰值为什么会出现，或者为什么少保存后峰值没有下降？

**短答：** min-cut 优化的是跨 FW/BW 边界保存量，而完整峰值是执行时间线上最大物理 live set。少保存
可能在 backward 集中触发重计算；alias 可能让底层 storage 仍被 pin 住；峰值也可能迁移到梯度、
optimizer 或 compiler workspace。因此 saved gain 只有在它释放了 dominant phase 的真实 storage，且没有
被新的 transient/fixed frontier 抵消时，才会转化为 overall peak gain。

**展开时按四层回答：**

1. D1：logical tensor 减少不等于独立 storage 被释放；
2. D2：重计算闭包可能在 backward 关键点前同时物化，形成 recompute wave；
3. D3：参数、梯度、optimizer 与 mandatory workspace 构成不可由 activation policy 消除的 fixed frontier；
4. D4/D5：fusion、layout、allocator 和 kernel workspace 会改变静态图到物理执行的映射。

**边界：** 这不是说 min-cut 必然导致峰值上升。若 after-FW activation 是 dominant frontier 且重计算
transient 较小，saved-memory 优化与 physical peak 可以高度一致。

### Q2：PeakAware 的寻优一定比开启 min-cut 或一般 AC 更优吗？

**短答：** 不一定。“更优”必须指定同一 measured peak 预算下的目标。PeakAware 的主张是提高预算满足
的可靠性，并在满足预算的方案中选择更高吞吐的 executable；当 min-cut 已落在 physical-peak Pareto
frontier 时，设计目标是保留并选择该 min-cut plan；只有真实 min-cut 已进入候选集、被实际执行且
冻结配对结果验证后，才能说 PeakAware 对它“保持不劣”。

**可声称条件：** 只有 G-1--G-7 通过后，才能依据 RQ-3/RQ-4 的冻结配对结果说“在这些 workload 和
协议下相对真实 baseline 改善”。不能从 proxy、合成图或旧矩阵推出全面优势。

### Q3：你是不是在证明 PyTorch min-cut 算错了？

不是。AOT min-cut 对其定义的 FW/BW boundary objective 有明确价值。本文指出该目标不等同于用户的
complete-step physical-peak constraint，并在目标外增加 phase/fixed/compiler-aware validation 与 repair。
这是目标层次的补充，不是把已有算法描述成实现错误。

### Q4：当前仓库里的 `torch_min_cut` 真的是 PyTorch min-cut 吗？

在 G-1 通过前不是。当前实现是 mandatory-only SAVE 的 `min-cut proxy`，provenance 也必须标为 proxy；
`block_checkpoint` 当前候选同样不是可直接等同于真实模型 block AC 的证据。正式比较必须接入真实
PyTorch partitioner/memory-budget baseline，或者在所有正文、图例和答辩中保留 proxy 名称，且不回答
“优于真实 min-cut”。

### Q5：为什么旧 64 条结果不能用？它们不是都成功了吗？

`64/64 ok` 只证明当时管线产生了成功记录。旧矩阵早于 plan-aware lowered-AOT runtime，候选可能共用
同一个 fallback callable，而且缺少当前 runtime adoption 字段。后处理 phase calibration 只能重算统计，
不能修复原始候选没有按不同 SAVE 计划执行的问题。因此旧效果矩阵状态是 `invalid`，正式效果必须用
当前 commit、当前 schema 和 runtime markers 重跑。

### Q6：为什么模型叫 BERT/GPT-2，但规模这么小？

代码中的 registry 名是历史工程名，论文按真实配置写作：`BERT-like-2L-64H` 和
`GPT2-like-2L-64H`，并在 T-1 列出层数、hidden、heads、sequence、参数量等。只有实际补跑标准配置后
才能使用 BERT-Base 或标准 GPT-2 名称。like 模型可用于机制与系统验证，但其结果不能外推为标准模型
规模结论。

### Q7：校准后误差很低，是否说明静态模型已经很准确？

不能。raw/static 不读取当前 workload 的 runtime baseline；all-save residual/phase calibrated 使用一次
实测 baseline 修正固定偏移或 dominant phase，属于 D4/D5 correction。答辩必须并列 raw 与 calibrated，
报告校准成本、低估/高估方向以及 P50/P90/max。校准后的精度只能支持“baseline-assisted online model”，
不能支持“纯静态模型达到同样误差”。

### Q8：phase calibration 100% 是否存在信息泄漏？

如果用同 workload 的 all-save measured dominant phase传播给候选，它是明确的 baseline-assisted
calibration，而不是独立预测。必须把数据依赖写进方法和图题，并保留 raw phase accuracy。它是否有用
应通过增加一次 baseline measurement 后对候选选择和预算满足的净收益评价，而不是只报校准准确率。

### Q9：根因诊断 100% 准确，是否能说明真实模型都可解释？

不能。现有 100% 只对应有限的手工合成 ground-truth cases，作用类似机制单测。真实模型通常没有唯一
人工真值，应该报告 evidence、counterfactual delta、cause frequency 和 confidence，不能把 heuristic
attribution 表述成确定因果，也不能把合成 precision/recall 外推到真实 workload。

### Q10：为什么 hints 在真实矩阵中没有改善？诊断是否无用？

这是需要保留的负结果。诊断可以解释收益缺口，但当候选空间缺少可改变的 SAVE 边界、fixed frontier
支配或 seed 已处于局部 Pareto 点时，hint 不一定改变最终方案。论文要用 diagnosis on/off 消融验证 hints
是否减少无效候选、编译次数或 violation；若仍为 neutral，就把优化收益 claim 收窄到解释和停止条件，
不把合成排序变化当真实收益。

### Q11：静态 cost ranking 相关性很弱，搜索还有意义吗？

弱相关说明不能只按静态分数选一个候选，也正是 Pareto Top-K 实测存在的理由。需要报告 Top-K regret、
最终预算成功率和编译成本，证明“粗筛选 + 少量实测”优于全编译或单点预测。若 Top-K 仍无法稳定包含
优胜方案，C-5 必须收窄，不能只以 cache 命中率掩盖排序问题。

### Q12：fixed frontier 主导时 PeakAware 能做什么？

参数、梯度、optimizer state/temporary 与 mandatory workspace 已接近或超过预算时，activation-only
rematerialization 无法满足约束。PeakAware 应尽早报告 infeasible 或低收益，避免无效重计算；用户需要
转向 sharding、offload、precision 或 optimizer-state 技术。识别不可行性是系统边界和负结果，不应包装
成峰值降低。

### Q13：为什么只优化 allocated peak，不优化 reserved peak？

论文默认目标是 `max_memory_allocated` 口径的 physical allocation，因为它更接近 live tensor/workspace
需求；reserved peak 受 allocator 保留池和碎片影响，作为辅助诊断并单独标注。两者都应保存，但不能在
同一图或结论中无标识替换。若用户实际受 reserved/OOM 行为影响，应额外报告 allocator 配置和 reserved
分析，而不是改写主指标。

### Q14：optimizer 不在 joint graph 中，为什么还能声称端到端？

“端到端”指完整 training step 的 measurement 和预算，包括 compiled/lowered FW/BW 与 eager optimizer；
不表示 optimizer 被捕获或优化进 joint graph。PeakAware 当前只选择 activation SAVE 集合，但用 optimizer
phase 的真实峰值验收计划，并把它计入 fixed frontier。答辩图中必须画出这条边界。

### Q15：如何证明不同计划真的执行了，而不是不同标签跑同一函数？

需要联合检查 plan identity、partition provenance、selected SAVE set、lowered FW/BW adoption marker、
fallback marker、输出/梯度/参数更新正确性，以及多步测量记录。只看 plan 名称或 JSON 中 selected strategy
不够。unsupported ABI 导致 whole-model checkpoint fallback 时，不能把多个细粒度候选当独立 runtime
策略比较。

### Q16：SAC 显存更低但速度更慢时，谁更优？

不存在脱离目标的单一答案。固定预算下先排除超预算方案，再比较吞吐；完整报告 strict/weak Pareto 和
dominated 点。SAC 更低峰值但更慢仍可能在紧预算区间是唯一可行解，PeakAware 吞吐更高但峰值更大也
不能称全面支配。最终表述必须限定到 matched measured peak 或同一预算。

### Q17：你的创新到底是算法、系统，还是测量工具？

核心是一个 systems contribution：识别 compiled rematerialization 的目标错位，建立 storage/phase/fixed/
compiler-aware 的峰值模型与 D0--D5 诊断，用证据驱动 SAVE repair，并将候选下发和实测闭环。它包含
模型、搜索机制和执行系统，但不是首次提出 rematerialization，也不是单纯 profiler。插件、ProfileDB、
cache 是支撑实现和摊销的机制，不单独算核心创新。

### Q18：这与 Checkmate、DTR、Rockmate 的本质区别是什么？

这些工作分别建立了广义 rematerialization 优化、在线驱逐和层次化求解的重要基础。PeakAware 不重复
它们的首创主张，而聚焦当前 compiled PyTorch 中 saved-boundary objective 到 complete-step physical
peak 的落差，强调 phase/fixed/compiler diagnosis、repair 和 actual executable validation。相关工作章
应按目标、决策空间、执行栈和测量口径精确比较。

### Q19：为什么需要 Top-K，为什么不对所有候选实测？

真实 AOT/Inductor 编译和稳定测量成本较高，全量实测会吞噬收益；只信静态第一名又会受 cost misrank
影响。Top-K 在预测峰值、cost 和候选多样性上粗筛，再对少数计划做正确性与 runtime measurement。
其合理性必须由 recall/regret、编译数量、cold/warm 时间和 amortization steps 共同支持。

### Q20：结果能否推广到大模型、多 GPU 或其他 PyTorch 版本？

当前结论边界是已测的静态 shape、单设备、当前 PyTorch AOT ABI、硬件和模型配置。BERT/GPT 还是 like
规格时，不能声称大模型结论；多 GPU 还会引入通信、sharding 和跨设备 frontier；版本变化可能改变
partitioner 和 compiler workspace。论文可以提出扩展方向，但效果只对冻结矩阵负责。

### Q21：旧数据完全无用吗？

旧数据可用于记录研发过程、发现候选问题、设计新协议和回归字段检查；它还提示 fixed frontier、ranking
和 hints 可能是重要风险。但因为执行语义失效，它不能支持端到端效果 claim，也不能与新矩阵混合计算
均值、胜率或置信区间。

### Q22：如果重跑后 PeakAware 没有显著优于 baseline，论文还能成立吗？

需要按证据收缩故事：

- 若 C-1/C-2 成立但 C-4 不成立，可定位为“目标错位的测量与诊断系统”，诚实报告 repair 无稳定收益；
- 若只在紧预算或特定 phase 成立，报告条件性收益和适用性分类；
- 若 min-cut 已处于 Pareto frontier，说明该 workload 上额外优化不必要；
- 若 fixed frontier 主导，强调 feasibility diagnosis；
- 不能用 synthetic 成功或校准精度替代缺失的端到端优势。

负结果不会自动否定论文，但必须重写题目、摘要和 C-4，使论点与证据一致。

## 6. 评委追问时的证据纪律

回答任何数字问题前，先确认四项：

1. 该数字是否来自当前冻结 commit 和当前 measurement schema；
2. baseline 是真实实现还是 proxy；
3. 模型名称是否与实际配置一致；
4. 指标是 raw/static、calibrated、allocated 还是 reserved。

不确定时的正确说法是“该结果尚未通过对应 gate，因此目前不作效果结论”，而不是引用旧矩阵填补。
答辩备份页应包含：G-0--G-9 状态、T-1 完整配置、runtime marker 示例、measurement protocol、全部负结果、
artifact manifest 和论点到 `EV-*` 映射。
