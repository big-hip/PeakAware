## 0. 全文论证合同

全文只回答一个中心问题：**saved activation 优化为何不能直接保证完整训练 step 的物理峰值预算，
以及 PeakAware 如何通过解释、修复、下发和实测选择闭合这条差距。**

写作时遵守以下顺序：

1. 先定义用户约束和现有目标的语义差异，再展示反例；
2. 从反例提炼一般机制，而不是把问题描述成单个 PyTorch bug；
3. 每个系统组件必须对应一个已定义的 failure mode；
4. 每个效果论点必须对应 `RQ-*`、`C-*`、`E-*`、`EV-*` 和 `F-*`/`T-*`；
5. raw/static 与 calibrated 结果并列，成功点、失败点和不可行预算同时报告；
6. 在 G-1--G-7 未通过前，效果数字只保留占位符，不从旧 artifact 抄入正文。

建议正文采用“问题与证据驱动”的八章结构，而非按项目研发时间顺序叙述。插件、ProfileDB、cache
属于实现或摊销机制，不单独设为核心贡献章。

## 1. 引言

### 1.1 目标

让读者在最短路径上接受三个前提：训练用户受完整 step 的 physical peak 约束；saved-memory 是有用
但不完整的代理；PeakAware 的研究对象是这两者在 compiled PyTorch 中的错位及闭环修复。

### 1.2 核心论证

- activation rematerialization 调节 memory-compute tradeoff，但 activation 不是完整峰值的唯一组成；
- AOT min-cut 可以有效优化 FW/BW 边界目标，但该目标不直接约束 FW、BW、optimizer 内部最大 live set；
- storage alias、recompute transient、fixed frontier、phase migration 和 compiler materialization 会让
  saved gain 与 overall peak gain 分离；
- 因此优化器必须以实测 physical peak 验收，并用诊断结果修复 SAVE 集合；
- 本文贡献由 C-1--C-5 构成，效果表述以完成对应 gate 为前提。

- 证据：只引用证据账本中与引言贡献逐项绑定且状态为 `frozen` 的 `EV-*`。

## 2. 背景与相关工作

### 2.1 目标

### 2.2 核心论证

- rematerialization 的一般 memory-time 优化问题已有充分研究，本文不争夺该问题的首创性；

- min-cut 的边界目标与完整 step physical peak 是不同目标，前者的价值不因本文工作而被否定；
- 现有工作分别擅长静态全局调度、在线驱逐、层次化结构或策略接口，PeakAware 聚焦 compiled PyTorch
  中目标错位的诊断、repair 与 runtime validation。

## 3. 动机与问题定义

### 3.1 目标

把“saved gain 没有转化为 peak gain”从观察上升为可测量、可分解、可证伪的优化问题，并明确可行性
下界和目标函数。

### 3.2 核心论证

- 给定 joint graph、执行配置、optimizer 和预算 B，决策变量是跨 FW/BW 边界的 SAVE 集合；
- 最终约束是完整 step measured allocated peak 不超过 B，目标是在正确性通过后优化稳态 step time 或
  有效吞吐；
- `strategy_expected_saved_gain`、`normalized_saved_gain`、`after_fw_gain` 和
  `overall_peak_gain` 构成从策略预期到物理实现的差距链；
- fixed frontier 可能使 activation-only 问题不可行，系统应报告 infeasible，而不是无效重计算；
- 一个 residual/recompute-wave 案例用于展示机制，真实模型分布用于证明问题不只是合成现象。

## 4. PeakAware 系统设计

### 4.1 目标

候选生成、plan lowering、正确性验证和 measurement，而不陷入实现细节。

### 4.2 核心论证

- 一次 joint capture 提供统一决策空间，并保留 storage、phase 和 provenance；
- 统一 IR 将逻辑 value、底层 storage、依赖、cost 和 SAVE policy 分离；
- 峰值模型输出候选的 phase/live-set 估计及置信边界；
- seeds 只提供候选起点，diagnosis/repair 和 Top-K 实测使选择目标与 physical peak 验收一致；
- plan identity、correctness 和 isolated measurement 防止“不同标签、同一 callable”的伪比较。

## 5. 峰值约束搜索与诊断

### 5.1 目标

解释 PeakAware 如何识别目标错位原因、生成可执行 repair、控制候选编译数量，并以物理预算和吞吐做
最终选择。

### 5.2 核心论证

- D0--D3 逐层引入 logical value、storage、recompute liveness 和 fixed/phase composition；
- D4/D5 是 compiler/runtime correction，不属于纯静态预测；
- 根因标签必须携带证据、置信度和 counterfactual repair，不只生成解释文本；
- min-cut、block、greedy 等 seed 可提供多样初解，但真实 baseline 与 proxy 必须分开；
- 多样性约束的 Pareto Top-K 缓解静态 cost ranking 弱的问题，最终只选择实测满足预算的计划；
- fixed frontier 超预算时提前返回不可行，是优化输出的一部分。

## 6. 实现

### 6.1 目标

### 6.2 核心论证

- 实现基于当前 PyTorch AOTAutograd 私有 ABI，捕获与 lowering 对 pytree、参数/缓冲区和切分 ABI

- runtime marker 用于证明 selected plan 是否采用 lowered-AOT、真实 min-cut/SAC 或 fallback；
- isolated worker、状态副本、warmup/repeats 和 phase reset 保证候选之间可比；
- cache 只复用满足版本、shape、dtype、设备和计划身份约束的结果。

## 8. 局限性与结论

### 8.1 目标

把适用边界、负结果和未解决问题转化为可信的结论，回答 PeakAware 何时有用、何时没有必要或无法
满足预算，而不是重复摘要或扩大主张。

### 8.2 核心论证

- PeakAware 的价值是让 activation planning 与 physical-peak constraint 对齐，不是证明 min-cut
  在其原目标上无效；
- 当 activation 支配峰值且不同 SAVE 集合改变 phase live set 时，peak-aware repair 更可能有收益；
- 当 fixed frontier 支配、所有候选同一 fallback 或 compiler variance 过大时，activation-only 选择
  可能无收益或不可辨识；
- Top-K calibration 提高可靠性但引入一次性成本和硬件/版本依赖；
- 后续工作可扩展到 optimizer graph、dynamic shape、offload/sharding 联合决策和更稳定的公开 API。
