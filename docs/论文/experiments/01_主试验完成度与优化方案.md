# 主试验完成度与优化方案

状态：面向 CCF-THPC 主实验的监督审计与优化版协议。

主试验问题：

> 给定 PyTorch 模型和显存预算，PeakAware 是否能比 saved-memory/min-cut 类方法更可靠地选择满足完整训练峰值预算的重计算方案，并保持较好的执行时间？

## 3. 主试验应优化成什么样

主试验不要问“估算准不准”，而要问：

```text
在同一 workload、同一输入、同一 optimizer、同一 backend 和同一显存预算下，
PeakAware 选择的可执行计划是否比 baseline 更少违约、更少 OOM，并在可行时更快？
```

最终实验单元应为：

```text
(workload, backend, budget_ratio, seed/pass, strategy)
```

每个单元必须记录：

- strategy name；
- strategy provenance：real / proxy / internal；
- plan id 与 effective SAVE set；
- runtime identity；
- correctness marker；
- measured FW/BW/OPT peak；
- measured complete-step peak；
- budget headroom；
- OOM / timeout / unsupported / correctness failure；
- measured step time；
- samples/s 或 tokens/s；
- estimated peak；
- estimated time；
- selected candidate rank。

## 5. Baseline 优化

### 5.1 必须补齐真实 baseline 身份

当前最大打回风险是 baseline provenance。优化优先级：

1. 真实 PyTorch memory-budget / min-cut baseline。
2. 真实 block checkpoint，即按模型 block/layer 插入 checkpoint，而不是保存前一半 forward values 的 proxy。
3. SAC matched matrix，确保 external SAC rows 能与主 records 按 workload/backend/budget 对齐。

如果短期补不齐，论文必须采用降级写法：

- `torch_min_cut_proxy`
- `block_checkpoint_proxy`
- `SAC external smoke`

并把结论限定为“相对当前可执行 proxy baseline”。

### 5.2 Baseline 表必须公开 provenance

主文表 T2 建议字段：

| Method | Source | Real/proxy/internal | Runtime identity | Correctness checked | Matched rows | Failure rows |
|---|---|---|---|---|---:|---:|
| All-save | internal | internal | yes | yes | ... | ... |

## 6. 测量协议优化

当前 EV-20 适合做初稿，但 final 主实验建议统一为：

- compile/warmup 和 measurement 分开；
- 每个 candidate 至少 warmup 5 step；
- 每个 candidate measurement repeats >= 20；
- 每个 workload/budget/backend 至少 5 个 process-level pass；
- CUDA Event phase timing 与 synchronized wall-clock 同时记录；
- 失败样本保留在分母；
- 每个 artifact 包含 manifest、environment、checksum、raw records、derived summary、figures 和 tables。

建议新增两个指标：

1. `budget_feasible_accuracy`：预测可行/不可行与实测是否一致。
2. `selected_regret`：PeakAware 选中候选相对同预算下实测最优可行候选的 step time regret。

主试验更应该报告：

```text
budget_satisfaction_rate
failure_rate
selected_regret
same_or_lower_peak_speedup
strict/weak Pareto win
```

而不是只报告平均 peak reduction。

## 7. 仿真准确性优化

新增硬要求：先证明“仿真时间/内存足够准确”，再讨论“能否用它选方案”。否则论文会退化成只靠实测 Top-K 的经验搜索，削弱 AtenIR 表征和 Costmodel 的贡献。当前阶段应把 Top-K/选择质量降为后续闭环，主线先做正确的仿真分析器。

### 7.1 内存峰值准确性

内存准确性要分四层报告，不能只报校准后数字：

| 层级 | 目的 | 必报指标 | 当前状态 |
|---|---|---|---|
| Raw L2/L2.5 | 纯生命周期/融合感知模型能力 | mean/P50/P90/max MRE，under-rate，phase accuracy | EV-20 raw simulation MRE 84.50%，不足 |
| D0--D3 | 解释 storage、liveness、recompute transient、fixed frontier 的贡献 | waterfall、dominant root cause、within-10% | 已有 layered accuracy，但需要图表化 |
| All-save calibrated | 证明少量实测能校准 allocator/runtime residual | calibrated MRE，calibration cost，是否泄漏候选答案 | EV-20 calibrated MRE 6.54%，可写但要标明不是纯静态 |
| Selected candidate | 证明最终选择的峰值预测可靠 | selected calibrated MRE，budget headroom error，violation prediction | EV-20 selected calibrated MRE 9.84%，接近可写线 |

建议最终验收阈值：

- calibrated memory peak mean MRE <= 10%；
- calibrated within-10% rate >= 80%；
- phase accuracy raw >= 70%，calibrated >= 90%；
- under-estimation 需要单独报告，尤其是导致 budget violation 的 under-estimation；
- selected candidate 的 budget headroom error 必须小于安全 margin，或触发实测回退。

内存仿真公式在论文中应明确写成：

```text
memory(t) =
    fixed_parameter_buffer
  + gradient_frontier(t)
  + optimizer_frontier(t)
  + saved_activation_liveness(t)
  + recompute_transient_liveness(t)
  + workspace_like_bytes(t)
  + calibrated_runtime_residual(phase)
```

注意：Costmodel 的 memory traffic 不能直接当作 `workspace_like_bytes(t)`；只有 op model 明确返回 allocator-visible workspace 时才能叠加。

### 7.2 时间仿真准确性

当前 EV-20 主要证明 Costmodel ranking 有中等相关性：

- candidate-time Spearman = 0.459；
- Kendall = 0.402；
- mean best-rank error = 0.865。

这能支撑 Top-K 必要性，但不足以支撑“仿真时间准确”。最终应补三层时间准确性：

| 层级 | 数据来源 | 指标 | 用途 |
|---|---|---|---|
| Op-level | Costmodel microbench/ProfileDB | per-op latency MAPE、P50/P90、coverage | 证明算子时间模型基础 |
| Subgraph-level | captured FW/BW subgraph replay | estimated vs measured phase time MAPE | 证明累积误差可控 |
| Candidate-level | Top-K measured candidates | step time MAPE、ranking Spearman/Kendall、selected regret | 证明选择不会被 misrank 主导 |

建议最终验收阈值：

- op-level covered hot ops latency MAPE <= 20%；
- FW/BW phase time MAPE <= 15%；
- candidate step time MAPE <= 15% after phase calibration；
- candidate-time Spearman >= 0.6，或明确写 Top-K measurement 是必要校正；
- selected regret <= 5% 或 <= 一个预设毫秒阈值。

时间仿真建议采用 phase-wise calibration：

```text
raw_time(op) = Costmodel(op, shape, dtype, layout, hardware)

phase_scale(FW) = measured_all_save_fw_time / raw_all_save_fw_time
phase_scale(BW) = measured_all_save_bw_time / raw_all_save_bw_time
phase_scale(OPT) = measured_all_save_opt_time / raw_all_save_opt_time

sim_time(candidate) =
    sum(raw_fw_ops) * phase_scale(FW)
  + sum(raw_bw_ops) * phase_scale(BW)
  + optimizer_time_model_or_measurement
```

如果 Costmodel coverage 不足，应把 uncovered op 明确标为：

- profiled fallback；
- empirical median fallback；
- conservative constant fallback；
- unsupported。

### 7.3 时间-内存联合准确性

最终主试验不能分开只看 time 或 memory，而要报告联合决策准确性：

| 指标 | 含义 |
|---|---|
| feasible decision accuracy | 预测满足预算的候选是否实测满足 |
| unsafe false-positive count | 预测可行但实测违约/OOM 的数量 |
| over-conservative false-negative count | 预测不可行但实测可行的数量 |
| selected regret | 选中候选相对实测最优可行候选的时间损失 |
| safe speedup | 在实测不超过 budget 的点上相对 baseline 的吞吐收益 |

论文主结论最好写成：

> PeakAware 使用 calibrated lifecycle memory model 保证预算安全，用 Costmodel ranking 缩小候选搜索，再通过 Top-K measurement 控制时间 misrank 风险。

这比声称“Costmodel 完全准确”更稳。

## 8. 结果写法优化

### 8.1 正结果应该这么写

推荐主结论模板：

> 在 EV-XX 覆盖的四个 workload、两个 backend 和五档相对预算下，PeakAware 在所有成功执行的选中计划中保持 0 budget violation；相对 all-save，平均提升吞吐 X%，并在 Y/Z 个 matched points 中达到 same-or-lower peak speedup >= 1。相对 min-cut/memory-budget baseline，PeakAware 降低了预算违约率，并在可行点上获得更低 step time regret。

### 8.2 失败记录应该这么写

不要回避 200 failed。把它纳入系统论文口径：

> 我们将 OOM、unsupported ABI、timeout 和 correctness failure 保留在分母中，因为预算选择系统的目标不仅是优化成功点，也包括识别不可行候选。失败记录用于计算 feasibility 和 coverage，而不是从结果中静默删除。

当前 EV-20 已将 200 条 failed records 拆成：

- `fixed_frontier_budget_infeasible`：80；
- `topk_no_candidate_passed_measurement`：120。

正式主实验仍建议继续保留更细分类：

- predicted infeasible；
- actual OOM；
- unsupported compiler/runtime；
- correctness failure；
- timeout；
- measurement infrastructure failure。

如果 failed 多数是基础设施问题，要补跑或单独剔除并解释。

### 8.3 Min-cut 反向峰值不降应放哪里

这个不应做主试验本体，而应作为主试验的动机/根因子实验：

- 第 2 章动机：一个 residual chain 例子说明 budget 降低但 BW peak 不降；
- 第 7 章结果：root cause 统计显示 `REMATERIALIZATION_WAVE` 是主要原因；
- 第 7 章消融：去掉 recompute transient 后会误判 saved gain。

## 9. 图表重排建议

主试验图表顺序：

1. **F1 System loop**：capture -> cost/liveness -> search -> executable -> measurement。
2. **F2 Budget satisfaction**：不同 method 在 50/65/80/95/100% budget 下的 violation/failure。
3. **F3 Pareto**：measured peak vs throughput，标出 selected plan。
4. **F4 Baseline comparison**：PeakAware vs all-save/block/min-cut/SAC 的 same-or-lower peak speedup。
5. **F5 Phase peak**：FW/BW/OPT peak stacked 或 heatmap。
6. **F6 D0--D5**：预测误差 waterfall。
7. **F7 Root cause**：REMATERIALIZATION_WAVE、WORKSPACE_GROWTH、FIXED_FRONTIER 等频率。
8. **F8 Memory accuracy**：raw vs calibrated peak parity，标明 under/over。
9. **F9 Time accuracy**：op/subgraph/candidate estimated vs measured time。
10. **F10 Costmodel ranking**：estimated vs measured time rank，Top-K regret。
11. **F11 Ablation**：no liveness/no transient/no fixed/no calibration/no Top-K。

表格顺序：

1. T1 workload manifest；
2. T2 baseline identity；
3. T3 budget satisfaction；
4. T4 throughput/Pareto；
5. T5 prediction error；
6. T6 failure taxonomy；
7. T7 overhead and amortization。

## 10. 下一步最短路径

如果时间紧，按这个顺序补：

1. **先修 baseline 名字和 provenance**：把 proxy 全文显式化，或补真实 baseline。
2. **补 SAC matched matrix**：否则 SAC 只能放相关工作/附录。
3. **补 warmup/repeats**：把 measurement repeats 提到 20，warmup >= 5。
4. **解释 failure taxonomy 并补跑必要 case**：EV-20 已把 200 failed 拆为固定前沿预算不可行 80、Top-K 无候选通过测量 120；下一轮要判断后者是预算真实不可行、候选生成不足，还是测量基础设施问题。
5. **补内存准确性表**：raw、D0--D3、calibrated、selected candidate 并列，重点报告 under-estimation。
6. **补 Costmodel 单算子/子图/候选时间误差**：支撑“Costmodel 和执行时间对齐”。
7. **补一张 per-op memory timeline**：证明 PeakAware 能解释 min-cut BW peak 不降。
8. **补 selected regret**：证明时间 misrank 不会破坏最终选择。
9. **补 actual-vs-simulated 时间-内存折线图**：横轴时间、纵轴 allocated memory，证明仿真曲线和真实执行曲线对齐。
10. **补 GPU 算力/访存利用率曲线**：同一时间轴下报告 GPU util、SM Active、Tensor Core utilization 或 DRAM throughput。

仿真曲线来源应采用以下组合：

```text

  1. 首选 AtenIR/lowered-FX liveness；

  4. Costmodel memory 只在 workspace-like 语义明确时作为 workspace_bytes 叠加；
  5. all-save residual calibration 只作为 runtime residual，不写成纯静态能力。
```

### 10.2.2 GPU 算力利用率采集

GPU 算力使用情况建议作为折线图副图，横轴同样使用 `time_us`。分三档实现：

| 档位 | 工具 | 字段 | 优点 | 风险 |
|---|---|---|---|---|
| L0 | `nvidia-smi dmon` / NVML sampling | GPU util、memory util、power、mem used | 简单，能做长时间曲线 | 采样粒度粗，不能归因到 op |
| L1 | `torch.profiler` | kernel time、CUDA time、memory events、op shapes | 与 PyTorch op 对齐 | 不直接给 SM Active/Tensor Core |
| L2 | Nsight Systems/Compute | SM Active、achieved occupancy、Tensor Core utilization、DRAM throughput | HPC/THPC 说服力强 | 采集成本高，集成复杂 |

论文主实验建议至少做到 L0+L1；如果时间允许，对 1--2 个代表 case 补 L2。GPU 利用率不应作为 PeakAware 选择的主目标，但可解释“时间为什么变慢/变快”：

```text
memory curve aligned but GPU util low   -> 重计算调度/launch overhead 可能主导
memory curve aligned and DRAM high      -> workspace/activation movement 可能主导
memory curve aligned and SM/Tensor high -> 额外计算本身主导
```

建议新增记录字段：

```text
selected_gpu_util_trace: [{time_us, gpu_util_percent, memory_util_percent, power_w, memory_used_mib}]
profiler_kernel_trace: [{time_us, duration_us, op_name, kernel_name, cuda_time_us, flops_estimate, bytes_estimate}]
selected_gpu_compute_summary: {
  status,
  sample_count,
  mean_gpu_util_percent,
  max_gpu_util_percent,
  mean_memory_util_percent,
  max_memory_util_percent,
  tensor_core_util_pct,
  dram_throughput_gbps,
  achieved_occupancy_pct
}
```

当前代码已补齐 L0 级字段：

- `measure_training_step_phases` 的 overall-step 窗口会尝试用 `nvidia-smi` 后台采样 GPU util、memory util、power、显存占用和 SM/MEM clock；
- `reporting.summarize_result` 会把 `gpu_util_trace` 与 `gpu_compute_summary` 放入 selected/measured candidate；
- `ExperimentRecord` 已新增 `selected_gpu_util_trace` 与 `selected_gpu_compute_summary`；
- `audit_timeline_readiness.py --require-gpu-util` 只把真实 sample 或 `status=ok` 且 `sample_count>0` 的 summary 视为 GPU-ready，`nvidia-smi_unavailable` 不算通过。

因此，下一轮主实验如果在 GPU 机器上运行，并且 `nvidia-smi` 可用，records 应能直接支持同一横轴下的内存折线和 L0 GPU 利用率副图。若 `selected_gpu_compute_summary.status=unavailable`，该 case 仍可用于主显存/时间结论，但 GPU 利用率分析必须标为缺失。

### 10.2.3 Astra-sim / Chakra 编排边界

FakeTensor / FakeTensorMode 适合放在 capture 层，用于在不真实分配激活张量的情况下获得 PyTorch/AtenIR 图、shape、dtype 和部分 alias 信息。它能避免“为了建模先跑爆显存”，但不能替代：

- CUDA allocator 实际采样；
- backward/rematerialization 执行顺序；
- workspace-like 临时分配；
- GPU kernel 利用率。

因此推荐路径是：

```text
FakeTensor graph capture
  -> AtenIR/lowered-FX graph and metadata
  -> Costmodel op time
  -> liveness/recompute memory event trace
  -> real execution sampled trace for calibration/validation
```

Astra-sim 可以作为后续编排/系统级扩展，但不建议作为当前单卡 AtenIR 内存折线图的主路径。推荐分工：

```text
PeakAware:
  AtenIR/lowered-FX op graph
  -> Costmodel/ProfileDB op time
  -> liveness memory event trace
  -> actual-vs-simulated memory timeline

Chakra ET:
  将 PeakAware event trace 导出为 compute/memory/communication node
  保留 dependency、duration、memory bytes 和 metadata

Astra-sim:
  消费 Chakra ET 做系统级调度/通信/多设备编排分析
  不直接解释 aten.addmm/aten.native_layer_norm_backward 等 AtenIR 语义
```

也就是说，Astra-sim 可用于论文展望或附录中的“编排扩展”，但当前主试验的折线图应由 PeakAware 的 Costmodel+liveness+runtime sampling 直接生成。否则会引入新的转换误差，反而削弱 AtenIR 级重计算内存表征主线。

### 10.4 Accuracy gate

新的实验 gate 建议命名为 `G-9 accuracy gate`：

| Gate | 通过条件 |
|---|---|
| G-9M memory accuracy | calibrated mean MRE <= 10%，within-10% >= 80%，unsafe false-positive = 0 或逐例解释 |
| G-9T time accuracy | candidate Spearman >= 0.6 或 selected regret <= 5%；若二者都不满足，必须降级为 Top-K empirical selection |
| G-9P phase accuracy | raw phase accuracy >= 70%，calibrated phase accuracy >= 90%，phase mismatch 进入 root cause |
| G-9C coverage | hot-op Costmodel/ProfileDB coverage >= 90%；uncovered ops 有 fallback provenance |
| G-9L timeline overlay | actual-vs-simulated memory timeline normalized RMSE <= 10%，peak time error 可解释 |
| G-9U GPU utilization | 至少提供 L0+L1 利用率曲线；代表 case 提供 L2 或说明缺失原因 |

若 G-9T 未通过，论文仍可写 PeakAware 预算选择可靠，但不能声称 Costmodel 时间仿真准确；只能写 Costmodel 用于候选筛选，最终时间由 Top-K measurement 校正。

## 11. 时间-内存折线图设计

你的判断是合理的：**横轴时间、纵轴内存的折线图应该成为主试验的核心图**。它比单个 peak bar 更有说服力，因为它能展示：

- peak 出现在哪个时间点；
- actual 和 simulated 是否在 phase boundary 对齐；
- min-cut 降 saved bytes 后是否出现 backward rematerialization wave；
- PeakAware 是否把峰值压到预算线以下；
- optimizer/fixed frontier 是否遮蔽 activation saving。

建议图形规范：

```text
x-axis: time_us 或 normalized_step_time
y-axis: allocated memory MiB/GiB
line 1: actual sampled allocated memory
line 2: simulated memory event trace
line 3: simulated + calibrated residual
horizontal line: memory budget
vertical bands: FW / BW / OPT phase
markers: actual peak, simulated peak, selected plan peak
lower panel: GPU util / SM Active / DRAM throughput
```

主图应该选 3 个 case：

1. **min-cut 不降反向峰值 case**：展示 backward rematerialization wave；
2. **PeakAware 成功满足预算 case**：展示曲线压到 budget 线下；
3. **optimizer/fixed frontier case**：展示 activation saving 被 optimizer peak 遮蔽。

图注必须说明 actual 采样粒度。若 actual 来自 phase anchor 而不是连续 CUDA memory sampling，图名应写 `phase-normalized timeline`；只有存在 `selected_actual_overall_sampled_memory_trace` 时，才能写 continuous sampled memory timeline。

## 14. 推荐最终主结论

最终论文的主结论应收束为：

> PeakAware 不是追求最低 saved activation 的策略，而是把重计算选择目标对齐到完整训练步 physical peak。通过 AtenIR 生命周期仿真、Costmodel 时间估计和 Top-K 实测闭环，PeakAware 能在预算约束下更可靠地选择可执行重计算计划；当 saved-memory/min-cut 目标与真实峰值错位时，PeakAware 能定位反向重计算波、fixed frontier 和 workspace growth 等根因，并避免把 saved bytes 下降误判为 physical peak 下降。
