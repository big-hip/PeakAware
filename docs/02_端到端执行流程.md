# PeakAware 端到端执行流程

## 1. 用户接口

```python
result = optimize_training(
    model,
    example_args,
    example_kwargs=None,
    loss_fn=loss_fn,
    optimizer=optimizer,
    memory_budget_bytes=20 << 30,
    config=PeakAwareConfig(...),
)
```

必要输入：模型、可产生标量 loss 的训练任务、输入签名、绑定该模型参数的 optimizer、目标硬件和
绝对显存预算。返回值包含最终计划、`TrainingStepExecutor`、峰值解释、cost provenance 和回退
信息。M2 插件通过 `PeakAwareConfig` 注入，不进入 M0 顶层 API。

## 2. 阶段 A：请求规范化

处理：

- 确认 `model.train()`；
- M0 固定 dtype 并关闭 autocast/GradScaler；M1 启用时将其配置纳入 request key；
- 校验 optimizer parameter groups 与 model parameters 的绑定并派生不可变 `OptimizerSpec`；
- 记录模型参数/buffer storage signature；
- 解析目标 CUDA device 和当前可用显存；
- 生成初始 request key。

失败条件：loss 不为标量、输入设备混乱、optimizer 绑定不一致、预算非法，或请求使用 M0 尚未支持
的 gradient accumulation、dynamic shape、FSDP/offload。

M2 才增加插件加载、冲突检查和 request validation hooks。

## 3. 阶段 B：Fixed Frontier 粗粒度预检查

在捕获和搜索前计算：

```text
parameter bytes
+ buffer bytes
+ expected gradient bytes
+ optimizer state bytes
+ optimizer temporary estimate
+ mandatory reserve
```

该阶段尚未获得 joint graph，只使用参数/状态总量和保守公式。输出
`CoarseFeasibilityReport`。若确定常驻的参数、buffer、optimizer state 等已超过预算，立即返回
不可行；其他情况只给出 headroom 预估，不代替捕获后的 phase-aware 结论。

M0 使用内置 optimizer 估算器；M2 的 `FixedMemoryProvider` 可覆盖特定 optimizer、FSDP 或自定义
状态。

验收：SGD、AdamW、fused AdamW 的 steady-state 固定内存估算有独立测试；预检查不能把未知
workspace 当作零，也不能因粗略上界过大而错误拒绝本可行请求。

## 4. 阶段 C：一次联合图捕获

首选路径：

```text
FakeTensorMode
-> torch.compile/AOTAutograd
-> intercept partition_fn input
-> capture pre-partition joint GraphModule
```

捕获内容：

- joint FX graph；
- node `meta["val"]`；
- module stack/source information；
- symbolic shape guards；
- decomposition 和 PyTorch 版本；
- parameter/buffer mapping；
- FW/BW 边界标记。

不能宣称绝对零开销：FakeTensor 不分配真实张量数据，但仍消耗 CPU 时间、FX/ShapeEnv 内存。

回退顺序：

1. M0 直接注册缺失 fake/meta kernel；M2 可由插件提供；
2. 调整 decomposition；
3. 按 graph break region 捕获，跨 region 输出强制 SAVE；
4. 经用户显式配置允许后使用最小真实输入捕获。

每级失败写入 `FailureRecord`，包含阶段、异常、已应用 adapter/plugin、是否恢复原状态和下一回退路径。
真实输入捕获默认关闭；启用后输入数据不落盘、不进入 capture/analysis/executable cache，捕获
结束必须恢复模型状态与梯度。若恢复失败，整个请求 fail closed，不继续使用该进程生成计划。

补丁点仅用于截获缺少公开 hook 的 partitioner 参数，必须由 `PatchSession` 自动恢复。

## 5. 阶段 D：构建 JointTrainingIR

处理顺序：

1. 为 op 和逻辑 value 分配稳定 id；
2. 解析 producer/consumer；
3. 识别 view、alias、tuple output 和共享 storage；
4. 标记 FW/BW phase 和边界值；
5. 执行 legality pass；
6. 发现 block、residual、attention、MLP region；
7. 构建 graph key。

输出不可变 `JointTrainingIR` 和 `IRValidationReport`。

验收：所有 value 有合法 producer/consumer；storage alias 不重复计数；graph outputs 被 pin；
mandatory SAVE 有解释字符串。

M2 事件 `after_ir_build` 允许只读分析或返回一个显式的新 IR，不允许原地修改。

IR 建成后重新运行精化 Fixed Frontier Analyzer，加入梯度物化顺序、mandatory values、阶段
临时量和已知 workspace，输出最终 `FeasibilityReport`。若此时 activation-only 不可行，停止
候选搜索并生成峰值下界解释。

边界固定为：`ActivationPlanner` 只生成 activation storage 的 SAVE/DROP；`StepPeakModel` 负责把
FW/BW activation、参数、梯度、optimizer state/temporary 和 workspace 合成完整 phase peak。

## 6. 阶段 E：Baseline 时间线

分别构建：

- all-save/default partition baseline；
- PyTorch min-cut baseline；
- block checkpoint baseline；
- fixed-state-only lower bound。

每个 baseline 输出：

```text
FW peak / after-FW retained
BW peak / recompute transient / gradient frontier
optimizer peak
overall peak
peak live storage explanation
```

该阶段用于校准仿真器，也用于判断当前 workload 是否值得继续搜索。

M1 对 default、min-cut 和 block checkpoint 执行基础策略缺口诊断，比较 strategy expected saved
gain、normalized storage gain、after-FW gain 和 overall peak gain。输出 primary root cause、
峰值快照和结构化 `RepairHint`，作为后续候选生成和搜索 seed 的输入。

M2 扩展为所有 `EvaluatedPlan` 的 D0--D5 诊断；baseline 阶段至少处理上述三类，搜索阶段处理进入
repair 或 Top-K 的 greedy、插件和 PeakAware 候选。策略没有自带预期模型时，strategy expectation 字段
标为 unavailable，但 storage、liveness 和 physical peak 诊断继续执行。

M2 事件：`after_baseline_analysis`、`after_plan_diagnostic`。

## 7. 阶段 F：Cost Provider 组装（M1 起）

M0 跳过 cost 组装，只评估配置中的手工/baseline plans。M1 使用 static fallback 或
`LegacyCostmodelAdapter`。M2 才由插件注册多个 provider，并由
`CompositeCostProvider` 按以下顺序查询：

```text
exact profile
-> interpolated profile
-> analytical Costmodel adapter
-> roofline fallback
```

所有 cost 必须携带 `source`、`confidence` 和硬件/软件版本。未知算子不允许静默返回零成本。

## 8. 阶段 G：候选与重计算闭包

M0 只接收配置中的 `saved_value_ids`，验证 legality 并推导 closure，不生成自动 move。M1 才生成
region 和 value 两级 SAVE 候选，并规范化为 storage-aware candidate。每个 move 必须列出
受影响 storage、alias/pinning values、峰值时刻实际释放字节和置信度；value bitset 只在 partition
lowering 阶段生成。对任意 SAVE storage set：

1. 从 backward required values 反向遍历；
2. 到最近 saved ancestor、parameter 或 graph input 停止；
3. 合并共享祖先；
4. 检查 barrier 和 RNG；
5. 得到 `RecomputeClosure`。

验收：all-save 闭包为空；all-legal-drop 闭包覆盖必要前向节点；非法值无法进入 DROP 集合。

## 9. 阶段 H：搜索（M1 起）

M0 不运行自动搜索，只对 all-save、min-cut baseline 和两个手工 SAVE plans 调用统一
`evaluate_plan(...)`，验证 closure、peak、partition 和运行期闭环。

### H1：Seed

生成：all-save、PyTorch min-cut、不同 `lambda` 的 cut、greedy bytes/cost、block checkpoint、
residual-boundary 和 wave-safe conservative plan。M2 可追加用户插件策略。

### H2：Simulation

对每个 plan 构建 alloc/free/recompute/gradient/workspace 事件流，输出峰值、step-time、
`max_recompute_live_bytes`、`recompute_span_ops`、`recompute_before_first_bw_op_bytes`、
`risk_score` 和 `confidence`。

### H3：Repair

超预算时，根据峰值 live set 选择 DROP move；若新增重计算反而增加 BW 峰值，则撤销 move 并
提高相关 residual boundary 的保存优先级。

Repair 必须消费诊断 hints：rematerialization wave 优先修正切点，fixed frontier 提前停止，
cost misrank 触发热点 profile，compiler/workspace 问题进入 Top-K 校正或安全裕量。

显式 early-stop policy 在 refined feasibility、每轮 repair 和 improve 后运行。activation-only
不可行时立即停止；headroom 过低、连续 move 无有效 peak gain、fixed frontier 主导或重算波硬约束
无法修复时，停止扩展并返回 reason、证据和 best-so-far plan。

### H4：Improve

对可行方案尝试 SAVE 高 cost 值和局部 swap，在预算内减少重计算时间。

### H5：Pareto

先按 `(estimated_peak, estimated_step_time)` 支配关系建立 frontier，再结合 `risk_score`、
`confidence`、峰值桶和 storage bitset 去重，输出 exploitation、exploration 和 conservative 三类
Top-K。

M2 搜索插件只通过 `SearchStrategy` 接口工作，不 patch 搜索引擎内部函数。

## 10. 阶段 I：Partition 下发

对 Top-K 方案：

```text
storage decisions -> lowered saved value ids
-> map to joint FX nodes
-> custom AOT partition_fn
-> concrete FW/BW GraphModule
```

结构验证包括 FW outputs、BW placeholders、tangents、RNG、参数映射和重计算节点集合。失败方案
被淘汰，不影响其他候选。

## 11. 阶段 J：aot_eager Dry-run 与 Inductor 校正

每个结构合法的 partition 先执行一次低成本 `aot_eager` dry-run，检查：

- FW outputs 与 BW placeholders 的数量、顺序、dtype、shape 和 stride；
- 参数、tangents、RNG state 的映射和消费顺序；
- loss、输出、梯度及 RNG 行为与 baseline 一致；
- 重计算节点集合与计划一致，且未跨越 legality barrier。

dry-run 失败直接淘汰候选并记录 `PartitionABIError`，不得进入昂贵的 Inductor 编译。dry-run 通过
只证明 partition ABI/语义成立，不替代真实 compiler workspace、峰值和性能校正。

随后每个合法方案：

1. 编译；
2. warmup；
3. 按 compiled FW/BW -> eager optimizer.step 顺序测量各 phase peak；
4. 测量稳定 step time；
5. 比较 loss 和 gradients；
6. 记录 compiler trace、cost residual 和失败原因。

M0/M1 串行验证候选，并在每次验证前后恢复 model/optimizer/RNG state；恢复失败则整个请求 fail
closed。M2 改为隔离 worker，实测结果写回 D5 反事实层并更新根因、置信度和修复建议。

禁止直接运行静态预测明显超过设备容量的方案。先使用安全裕量和估计排序，必要时从最保守
方案开始验证。

## 12. 阶段 K：选择与缓存演进

只在 `measured_peak <= user_budget` 的候选中选择最快方案。M0 不实现持久化 cache；M1 可使用进程
内 graph/closure/result memoization；M2 才实现以下三层持久化缓存并独立失效：

- capture cache：保存一次捕获的 joint graph、guards 和 capture provenance；由模型/输入签名、
  PyTorch、decomposition 及 capture 插件决定；
- analysis cache：保存 JointTrainingIR、alias/storage、legality、regions、liveness 和 fixed frontier；
  由 capture key、optimizer/fused mode、fixed-memory provider、device/allocator assumptions、analysis
  schema/version 及 IR/analysis 插件决定；其中保存预算无关的 fixed timeline/lower bound，
  `FeasibilityReport` 按当前 budget 派生；
- executable cache：保存 plan、partition ABI 摘要、aot_eager dry-run 结果、Inductor artifact、实测
  peak/time 和 correctness；由 analysis key、cost/search/partition/validation 配置和编译环境决定。

executable 层内部使用两个可组合 fingerprint：`plan_evaluation_key` 绑定 cost DB、预算和 search
policy，`compiled_artifact_key` 绑定 lowered plan fingerprint、guards 和编译环境。cost/search 改变时
重新评分和选 plan，但若 lowered plan 与编译环境未变，可复用已有 artifact；compiler/partition
变化则必须重编译。这样保持三层外部 API，同时避免把搜索失效和编译失效粗暴绑定。

两个 fingerprint 分别包含：

```text
plan_evaluation_key:
  analysis key + optimizer/fused mode + cost database version
  + search/risk policy version + budget bucket

compiled_artifact_key:
  lowered plan fingerprint + parameter/buffer signature
  + input shape/dtype/stride guards + device capability
  + PyTorch/CUDA/Inductor version + partition/compiler plugin version
```

预算变化只重新派生 feasibility 并失效 executable selection/search，不触发重新捕获或重建预算无关
analysis；cost database 或 search policy 变化不失效 capture/analysis；PyTorch/decomposition、shape
guard 或 alias analysis schema 变化必须级联失效下游层。任何缓存均不包含用户训练数据。

## 13. 训练运行期

`TrainingStepExecutor.step()` 固定执行：

```text
zero_grad policy
-> selected compiled FW/BW
-> eager optimizer.step()
-> return loss/metrics
```

运行期不重复搜索，也不接管 optimizer state 的所有权。若 shape guard 失效、M2 插件版本变化或
runtime peak 超过安全阈值：

1. 停止使用当前计划；
2. 尝试已验证的保守 executable；
3. 必要时触发新 graph key 的离线优化；
4. 记录回退原因。

## 14. 可选 Microbatch 外层（M3）

若启用吞吐优化，按 microbatch 枚举完整 K 阶段，并选择：

```text
argmax_m,plan useful_samples / measured_step_time
```

不同 shape 默认具有不同 graph key。动态 shape 共享图必须有单独正确性和性能证据。

## 15. 最小运行闭环

第一条可运行链只要求：

```text
Tiny residual model
-> fake joint capture
-> storage IR
-> all-save/min-cut/two custom SAVE plans
-> static peak
-> custom partition
-> gradient check
-> compiled FW/BW + eager optimizer step
-> CUDA phase peak/time
```

该闭环完成后再扩展搜索算法、Costmodel 和大型模型，避免多个不确定层同时开发。
