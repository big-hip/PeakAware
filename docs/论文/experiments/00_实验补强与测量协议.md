# 实验补强与测量协议

本文档只定义实验设计、测量协议和 `E-*` 的通过条件，不保存最终结果数字。结果状态、artifact
路径和校验和统一登记到 evidence ledger；术语、模型名称和统计公式以 `02_术语与口径.md` 为准。

## 1. 实验目标与当前证据边界

正式实验必须回答 `RQ-1`--`RQ-5`，并为 `C-1`--`C-5` 提供可证伪证据。旧 64 条效果矩阵早于
plan-aware lowered-AOT runtime，不能证明不同 SAVE 计划被分别执行，状态固定为 `invalid`。离线重算
summary、phase calibration 或重新绘图都不能恢复其效果证据资格。

以下项目在主矩阵启动前必须完成：

- `G-1`：接入真实 AOT min-cut；当前 mandatory-only `min_cut_proxy` 只可用于实现诊断；
- `G-1`：实现真实 block AC 和 SAC 路径，并证明各方法确实下发不同 runtime；
- `G-2`：使用 `BERT-like-2L-64H`、`GPT2-like-2L-64H`，除非另行补跑标准规格；
- `G-3`：每条候选记录包含 plan identity 和 runtime adoption marker；
- `G-6`：CUDA Event、同步 wall clock、phase peak 和完整 step peak 的采集协议通过资格测试。

任何前置条件失败时，只允许运行 smoke 和调试实验，不得把结果升级为 `frozen`。

## 2. 实验因子与冻结层级

### 2.1 核心工作负载

`T-1` 的最终规格由图表文档维护；本实验只规定覆盖约束。

| 架构族 | 论文名称 | 核心输入 | 扩展轴 | 必须覆盖的 optimizer |
|---|---|---|---|---|
| CNN | ResNet-50 | 固定 224x224 | microbatch | SGD，扩展点可用 AdamW |
| Vision Transformer | ViT-B/16 | 固定 224x224 | microbatch | AdamW |
| Encoder Transformer | BERT-like-2L-64H | 固定静态 sequence | microbatch、sequence | AdamW |
| Decoder Transformer | GPT2-like-2L-64H | 固定静态 sequence | microbatch、sequence | AdamW |

核心矩阵每个架构先冻结一个 canonical workload configuration，包括模型规格、batch/microbatch、
输入 shape、dtype、optimizer 和 loss；seed 只标识独立重复，不定义新的 workload。`backend x budget`
定义实验 cell，方法、hints 和 pass 是 cell 内配对条件。跨 workload 推断时，抽样单位始终是唯一
workload configuration，不能把 backend、预算、seed、hints 或 pass 复制成更多 workload。

扩展矩阵在每个架构选取至少两个额外压力点。优先增加 microbatch；Transformer 再增加 sequence。
扩展点用于检验趋势，不替代核心矩阵。

### 2.2 执行后端

每个核心点必须分别运行：

1. `aot_eager`：验证 partition、lowered FW/BW 和方法差异；
2. `inductor`：验证编译物化、workspace、稳定吞吐和完整物理峰值。

两种 backend 的数据不得合并为一个样本。optimizer 保持在 joint graph 外，但必须纳入完整 step
计时和 `FW/BW/optimizer` phase peak。若某方法不能在某 backend 上保持其原始语义，应记录为
`unsupported`，不能静默切到 whole-model checkpoint fallback。

### 2.3 主 baseline

核心矩阵至少包含以下五种方法：

| 方法 | 必须满足的实现身份 | 公平性要求 |
|---|---|---|
| all-save | 同 backend、无 activation recomputation | 作为物理预算标尺和校准成本来源 |
| AOT min-cut | PyTorch partitioner 产生的真实 SAVE 集合 | 保存 partitioner 配置、memory budget 和源码版本 |
| block AC | 按模型真实 block/region 放置 checkpoint | 冻结 region 边界，不得用“保存前半 values”代理 |
| SAC | PyTorch Selective Activation Checkpoint policy | 保存 policy、op 决策和上下文实现 |
| PeakAware | seed、诊断、repair、Top-K、实测选择完整启用 | 保存候选全集、被测 Top-K 和最终 executable identity |

`min_cut_proxy`、当前 `block_checkpoint` proxy、greedy seeds 可以进入机制消融，但不得出现在主图中
冒充真实 baseline。若真实 min-cut、SAC 或 block AC 未完成，`E-1/E-3/E-4` 不得启动正式运行。

### 2.4 相对物理预算

对每个 `(workload configuration, backend, dtype, optimizer)` 先执行独立 all-save 标定，取五个独立
进程中完整 step allocated peak 最大值的中位数为 `P_ref`。冻结预算：

```text
B_r = floor(r * P_ref), r in {0.50, 0.65, 0.80, 0.95, 1.00}
```

- `P_ref`、舍入规则和字节值写入 manifest 后才可运行其他方法；
- 所有方法共享同一组 `B_r`，不得按方法自身峰值重新定预算；
- 预算判定使用每个独立进程的完整 step 最大 allocated peak，不使用 repeats 的均值；
- reserved peak 同步保存，但不参与主预算判定；
- 若 50% 低于 fixed frontier，保留为预期不可行点，验证系统能否明确返回 infeasible；
- 若五点均无预算压力，增加夹在 fixed frontier 与 `P_ref` 之间的插值点，不能删除既定五点；
- 绝对 GiB 预算只用于复现说明或硬件容量限制，不替代相对预算主分析。

`P_ref` 标定进程不参与方法效果的置信区间，防止同一观测既定义预算又评价预算。

### 2.5 Baseline 调参与 held-out 评价

block AC、SAC 和 AOT min-cut 都可能产生多个策略强度，不能拿它们的单个默认点与 PeakAware 的
Top-K 最优点比较。每个方法预先冻结可枚举的 policy family：block region/间隔、SAC policy、
min-cut saved-memory ratio，以及 PeakAware seeds/repair/Top-K。禁止根据主评价结果新增有利变体。

- 为每个 `(configuration, backend)` 设置 tuning cohort 和 evaluation cohort；二者使用不同进程 seed；
- tuning cohort 对每个方法使用相同的候选编译上限、wall-time 上限和最多 3 个独立进程；
- 对每个物理预算 `B_r`，只用 tuning cohort 选择该方法中“满足预算且中位 step time 最低”的固定
  policy；无可行 policy 时冻结为 infeasible；
- evaluation cohort 使用至少 5 个全新独立进程执行已冻结 policy，不再根据评价 peak/time 改选；
- all-save 只测一次参考 policy，并关联到五个预算，不因重复关联而增加样本数；
- 主 Pareto 可额外展示全部预注册 policy 的原始点，但 headline comparison 使用 held-out policy；
- PeakAware 的 all-save calibration 和 Top-K 实测都计入 tuning 成本；baseline 的 policy sweep 成本
  同样计入，分别报告方法自身成本与“统一候选上限”下的结果。

若 GPU 预算不足以实施 held-out 设计，结果只能标为 `provisional`；不得用同一 repeats 同时调参和
报告置信区间。

## 3. 通用测量协议

### 3.1 独立进程和运行顺序

- 每个 `(configuration, backend, budget, method)` 至少运行 5 个全新独立进程；
- 每个进程重新构造模型、输入、optimizer 和 CUDA context，不跨方法复用状态；
- 在每个 `(configuration, backend, process replicate)` block 内，用预先生成并保存的 seed 随机化
  方法与预算顺序，降低温度、allocator 和 cache-order 偏差；
- cold-cache 与 warm-cache 是不同实验条件；主效果矩阵使用 cold executable identity，摊销实验单独测 warm cache；
- 每个方法使用相同输入、初始化 seed、loss、zero-grad 语义、精度和 optimizer 超参数。

### 3.2 Warmup、repeats 与计时

- 编译、autotune 和 warmup 不进入 steady-state 统计；
- `aot_eager` 至少 warmup 5 step，Inductor 至少 warmup 10 step，并要求最后 5 个 warmup 的 step
  time 无单调下降趋势；不满足时继续 warmup，最多 30 step；
- 每进程每点至少 20 个 steady-state repeats；论文关键主点建议 50；
- phase 与完整 step 均用 CUDA Event 计时，Event 前后正确 record，并在读取 elapsed time 前同步；
- 同时用 `perf_counter` 包围同一同步区间记录 wall clock；
- `E-0` 要求 CUDA Event 与同步 wall-clock 的进程内中位数偏差得到记录并解释，不能假定两者相同；
- compile、capture、search、profile、candidate validation 和 steady-state step time 分开保存。

吞吐由每次 steady-state repeat 的实际 samples 或 non-padding tokens 除以 Event 时间计算。跨 workload
的 speedup 只对 matched baseline 比值取几何均值，不直接平均 samples/s 或 tokens/s。

### 3.3 显存采集

- 在 measurement window 前同步并重置 CUDA peak statistics；
- 记录完整 step allocated/reserved peak，以及 FW、BW、optimizer 三个 phase 的 allocated/reserved peak；
- phase 之间的 reset 可能改变观测窗口，完整 step peak必须由另一次不重置的同计划执行取得；
- 保存 after-FW retained、saved logical bytes、storage-normalized saved bytes 和 recompute transient 估计；
- 预算 violation 由 `measured_peak_allocated_bytes > B` 定义，恰好等于预算视为满足；
- OOM 前若可取得 allocator snapshot 或已完成 phase，保存局部证据，但不得补造 peak 数字。

### 3.4 正确性

性能测量前，每个新 `(method, configuration, backend)` 必须相对 all-save 参考完成：

- 相同 seed 和初始化下的 forward output 与 loss；
- 每个 parameter gradient 的绝对/相对误差和 finite 检查；
- 至少 3 个 optimizer step 后参数差异；
- dropout/RNG 状态重复性；
- tied/shared weight、复杂 pytree 和 alias 场景的专项测试；
- plan identity 与实际 FW/BW GraphModule identity 对应；
- runtime marker 证明真实 AOT partition、AC 或 SAC 路径被采用。

容差由 dtype 分层冻结，不能在看到失败后逐点放宽。correctness failure 不进入吞吐/Pareto，但作为
失败结果进入分母和 `T-*`。

### 3.5 失败分类

每个计划必须落入且只落入以下状态之一：

| 状态 | 判定 | 处理 |
|---|---|---|
| `ok` | 正确性通过、测量完成 | 进入对应统计 |
| `budget_violation` | 完成执行但 peak 超过 B | 进入预算失败分母，仍可画原始 Pareto 点 |
| `oom` | CUDA allocator OOM | 进入预算失败分母，不推断缺失 peak/time |
| `timeout` | compile 或执行超过冻结上限 | 进入失败分母，保存阶段和 elapsed time |
| `correctness_failure` | 数值或 runtime identity 失败 | 从性能聚合排除，但进入可靠性分母 |
| `unsupported` | 方法在该 backend 无真实语义 | 单列覆盖率，不伪装为 fallback |
| `infra_failure` | 机器、驱动、磁盘等非方法故障 | 不计方法胜负；修复后重跑同 run slot |

compile timeout 与 steady-state timeout 分开冻结。OOM、timeout 和 correctness failure 不得从 raw
records 删除；重跑生成新 attempt，并保留被替代 attempt。

## 4. 统计计划

### 4.1 单位与配对

- 主抽样单位：唯一 workload configuration；`backend x budget` 是预注册实验 cell，独立进程/seed
  是 cell 内重复测量，方法与 hints 是配对条件；
- 同一 workload 的多个 backend/预算不得在跨 workload bootstrap 中当作独立样本；需要汇总时先在
  workload 内按预注册规则聚合，再以 workload 为 cluster 重采样；
- matched comparison：同 configuration、backend、budget、replicate 的 baseline 与 PeakAware；
- hints on/off、Top-K 和 matrix pass 是配对条件，不是额外 workload；
- 同一进程内的 20--50 repeats 描述稳态噪声，不得当作 20--50 个独立样本；
- 主图同时给逐 workload 点，避免总体均值隐藏架构差异。

### 4.2 汇总量

- step time：先取每进程 median，再对 5 个进程报告 median、P10/P90 和 bootstrap 95% CI；
- physical peak：预算判定用每进程 repeats 最大值，展示时报告进程级 median、P10/P90 和最大值；
- speedup：先形成配对比值，再跨 configuration 求几何均值和 bootstrap 95% CI；
- budget reliability：报告 violation、OOM、timeout、correctness failure、unsupported 的计数和比例；
- 模型误差：按 `02_术语与口径.md` 以 measured peak 为分母，报告 signed error、MAPE、P50、P90、max；
- 排序：每 workload 报 Spearman、Kendall、best-rank regret 和 Top-K regret，再跨 workload 汇总；
- 多重比较：主比较预先限定为 PeakAware 对四个主 baseline；探索性比较明确标记，不作选择性显著性叙述。

主结论优先使用效果量、区间和逐点胜负；p-value 只能作为补充。预算满足率的分母必须能由 raw
records 重建。

## 5. `E-*` 实验矩阵

### E-0 测量资格与 runtime 身份

**目的**：解锁 `G-1/G-3/G-6`，证明测量器和五种方法身份可信。

**矩阵**：四架构各一个最小可运行点，双 backend，五种主方法；每点 2 个独立进程、20 repeats，
只作 qualification，不进入论文效果统计。

**必须输出**：Event/wall-clock 对照、phase 与 overall peak、plan/runtime identity、correctness、失败
分类、环境 fingerprint。

**停止条件**：任一方法退化到共享 callable、runtime marker 缺失、phase 最大值与 overall window
存在无法解释的矛盾、正确性失败，立即停止主矩阵并返工。

### E-1 Saved-memory 与物理峰值错位

**回答**：`RQ-1`，支撑 `C-1`。

**矩阵**：四架构、双 backend、五个相对预算；重点比较 all-save 与真实 AOT min-cut，并保留 block
AC、SAC 和 PeakAware 作为参照。完整执行 5 个独立进程。

**观测**：strategy expectation、logical/storage saved、after-FW retained、BW transient、fixed
frontier、phase migration、overall peak gain、D0--D5 delta。

**通过条件**：能够量化错位分布并给出无错位/反向/被 fixed frontier 遮蔽的全部点；若真实模型
中未观察到错位，`C-1` 必须降级，不能用 synthetic reproducer 替代普遍性证据。

### E-2 峰值模型和 phase 预测

**回答**：`RQ-2`，支撑 `C-2` 的模型部分。

**矩阵**：复用 `E-1/E-3` 中所有实测候选，按 D0、D1、D2、D3、D4、D5 保存逐层预测；raw/static
与 all-save residual/phase calibrated 分开。

**观测**：signed error、APE、P50/P90/max、phase accuracy、feasible classification、低估尾部；按
架构、backend、预算和 peak phase 分层。

**通过条件**：每层输入可追溯，raw 与 calibrated 并列，校准额外运行成本被计入；若 D4/D5 才使
误差下降，应将其表述为在线校正能力，不得宣称纯静态准确。

### E-3 紧预算满足率

**回答**：`RQ-3`，支撑 `C-4` 的可靠性部分。

**核心评价规模**：all-save 为 `4 架构 x 2 backend x 1 policy x 5 独立进程`；四个预算感知方法为
`4 架构 x 2 backend x 5 budget x 4 method x 5 独立进程`。每点至少 20 steady-state repeats；每个
configuration 使用同一冻结 `P_ref`、held-out policy 和随机顺序表。tuning cohort 另行计数。

**观测**：feasible、budget violation、OOM、timeout、correctness failure、fallback/unsupported、
最大可行 microbatch。

**通过条件**：四架构和双 backend 无缺失 slot；失败均分类；真实 baseline 覆盖率单列。若
PeakAware 在预注册主比较中没有改善，应保留负结果并调整 `C-4`，不能增加事后筛选预算。

### E-4 相同实测峰值下的吞吐与 Pareto

**回答**：`RQ-4`，支撑 `C-4` 的性能部分。

**矩阵**：复用 `E-3`，增加每架构至少两个 microbatch/sequence 压力点；若资源不足，扩展矩阵可只
运行 all-save、最佳真实 baseline 和 PeakAware，但核心矩阵不可裁剪。

**观测**：measured peak、Event step time、samples/s 或 tokens/s、strict/weak Pareto win、dominated
点、最大可行 workload size。

**通过条件**：比较使用相同或更低实测 peak，不按 saved bytes 配对；报告逐点胜负和几何平均
speedup。SAC 更省峰值但更慢等 trade-off 保留在 frontier，不强行归为 PeakAware 失败或胜利。

### E-5 根因诊断与 hints 闭环

**回答**：`RQ-1/RQ-3`，支撑 `C-2`。

**合成矩阵**：分别构造 alias pinning、recompute wave、shared recompute expansion、fixed frontier、
phase migration、workspace growth、cost misrank 和 measurement noise；每类至少 3 个参数化实例。

**真实矩阵**：对 `E-1` 的错位点运行 hints on/off 配对条件，保持候选预算、Top-K 和随机 seed 相同。

**观测**：合成 precision/recall/F1；真实点只报告 evidence、counterfactual delta、confidence、候选
顺序变化、无效 repair 数、搜索迭代、预算满足和最终 frontier。

**通过条件**：诊断至少能改变一个可验证的搜索决策或提前终止不可行搜索；若真实 hints 仍为
neutral，只保留解释性贡献，不声称优化收益。

### E-6 组件消融

**回答**：`RQ-2/RQ-3/RQ-5`，检验每个系统组件是否必要。

**配置**：完整 PeakAware 对照以下单变量消融：去 storage/alias、只优化 saved bytes、去 fixed
frontier、去 diagnosis、去 hints、去 repair、去 Top-K runtime correction、FLOPs/ProfileDB cost、
不同 Top-K、不同 safety margin。proxy seeds 只在此处出现并明确标名。

**矩阵**：四架构 `aot_eager` 全覆盖；Inductor 至少覆盖每架构 65% 和 95% 两个预算。每点 5 独立
进程。若预实验显示某消融完全等价，先验证代码路径确实不同再解释结果。

**通过条件**：每个声称必要的组件至少对应一个 failure mode 和可测效果；无效果组件降为工程实现，
不单列贡献。

### E-7 搜索、Top-K、cache 与摊销

**回答**：`RQ-5`，支撑 `C-5`。

**矩阵**：四架构，选 65% 和 95% 预算；Top-K 取 `{1, 3, 5, 10}`；分别运行 cold capture/cache、
warm analysis cache、warm executable cache。至少 5 独立 cold run；warm run 与相应 cold identity 配对。

**观测**：capture、IR、analysis、search、profile、compile、candidate validation 时间，候选数量、
cache hit/miss、最终 plan regret、稳态节省时间和 amortization steps。

**通过条件**：摊销分母和 workload horizon 明确；若静态 ranking 弱，必须报告 Top-K regret，不能只
展示 cache hit rate。

### E-8 Fixed frontier 与不可行预算

**回答**：`RQ-3`，补强 `C-1/C-2` 的边界。

**矩阵**：四架构，改变 optimizer、microbatch/sequence；至少覆盖一个 activation-dominated、一个
fixed-frontier-dominated 和一个 50% 预期不可行点。optimizer 差异作为独立 configuration。

**观测**：fixed lower bound、activation headroom、预测/实测可行性、停止搜索次数和误判类型。

**通过条件**：不可行判断不依赖候选运行后的 OOM 才产生；假阳性和假阴性均报告。

### E-9 稳健性与顺序偏差审计

**目的**：证明主结果不由温度、首次编译、allocator 历史或单一 seed 驱动。

**矩阵**：从 `E-3` 每架构抽取 65%、95% 两个预算，反转方法顺序并更换至少 3 组顺序 seed；记录
GPU 温度、时钟、功耗（可得时）和后台进程。

**通过条件**：顺序效应进入不确定性分析；若结论随顺序翻转，增加独立进程并修正运行隔离，不能
选择有利顺序。

## 6. 分阶段运行与停止规则

1. 先完成 `E-0`，再标定 `P_ref`；资格失败时禁止并发扩展矩阵。
2. 先跑每架构一个 `aot_eager` 65% 点作为 canary，再跑完整 AOT 核心矩阵。
3. AOT 通过后，对 Inductor 先跑四架构 95% canary；只有 runtime identity、正确性和稳态条件均通过
   才扩展到五预算。
4. 每完成 10% raw slots，自动检查 schema、重复 run ID、缺失 runtime marker、异常零峰值和方法
   coverage；失败率超过 10% 时暂停派发并根因分析。
5. 出现共享 callable、baseline proxy 混入、模型名称错误或预算由候选自身定义，整批 run 标为
   `invalid`，修复后使用新 `run_id` 重跑。
6. 单点 OOM/timeout 是有效结果；基础设施连续三次失败才暂停该机器，不将方法失败改标为 infra。
7. 资源不足时优先级为 `E-0 -> E-3 -> E-1/E-2 -> E-4 -> E-7 -> E-5/E-6/E-8/E-9`；不得通过
   减少四架构、五预算、双 backend 或五独立进程来保留低优先级消融。
