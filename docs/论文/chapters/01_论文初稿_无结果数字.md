## 摘要

编译训练系统通常通过 activation rematerialization 降低跨前向和反向边界保存的激活量，但
saved-memory 目标并不直接等价于完整训练 step 的物理峰值。本文研究静态 shape、单设备 PyTorch
编译训练中的 activation SAVE/RECOMPUTE 选择问题，关注 forward、backward 和 optimizer phase
共同决定的 allocated physical peak。

本文提出 PeakAware：它在一次 AOTAutograd joint graph 捕获后构建 storage-aware IR，使用
D0--D5 层级解释 saved-memory 预期收益与 runtime peak 之间的差距，并以诊断结果修复 SAVE
集合。系统随后只对多样化 Pareto Top-K 候选进行 lowering、正确性验证和完整 step 实测，最终选择
满足物理预算的 executable。结果数字将在 `EV-10`--`EV-19` 冻结后填入；冻结前摘要不得写峰值降幅、
吞吐提升或 baseline 胜率。

## 1 引言

GPU 显存限制了训练时可使用的 batch size、sequence length 和模型规模。Activation checkpointing
及 AOTAutograd min-cut 类方法通过少保存部分前向中间值、在反向中重计算它们，提供了常用的
memory-compute tradeoff。

然而，在编译训练中，减少 saved activation 并不必然带来完整训练 step 峰值的同等下降。逻辑 tensor
可能共享底层 storage；反向阶段可能出现重计算瞬时量；梯度、参数、optimizer state 和 compiler
workspace 也可能成为新的峰值来源。因此，本文将目标从“少保存多少 activation”转为“是否满足完整
step 的 physical peak 预算”。

本文围绕五个研究问题展开：`RQ-1` 刻画 saved-memory 与 physical peak 的错位；`RQ-2` 评估
storage/phase/fixed/compiler-aware 模型的预测能力；`RQ-3` 比较紧预算下的满足率；`RQ-4` 比较同
实测峰值下的吞吐 Pareto；`RQ-5` 分析 Top-K、profiling 和 cache 成本。

本文贡献对应 `C-1`--`C-5`，最终表述必须由冻结证据支持。若真实 baseline 或主矩阵未通过 gate，
贡献将收缩为目标错位刻画、诊断和可执行原型。

## 2 背景与问题定义

本章定义 PyTorch AOTAutograd joint graph、SAVE/RECOMPUTE 语义、saved activation、storage、
after-FW retained、recompute transient、fixed frontier 和 allocated physical peak。论文默认
optimizer 位于 joint graph 外，但位于 complete-step measurement 内。

问题定义：给定静态 shape 单设备训练任务、候选 SAVE 集合和物理峰值预算 `B`，系统需要选择一个
数值正确的 executable，使完整 step 的 allocated peak 不超过 `B`，并在预算内优化稳态 step time
或 throughput。

## 3 目标错位与诊断模型

本章解释为什么 logical saved bytes、storage-normalized saved bytes、after-FW retained memory 和
complete-step peak 可能给出不同结论。PeakAware 使用 D0--D5 层级逐步加入 storage alias、
recompute liveness、fixed frontier、compiler correction 和 runtime measurement。

本章现在可以写机制和公式，但真实模型中的错位比例、dominant cause frequency 和 phase migration
必须等待 `EV-10`、`EV-11`、`EV-12` 冻结。

## 4 PeakAware 系统设计

PeakAware 的流程为：joint capture、storage-aware IR、seed generation、D0--D5 diagnosis、
SAVE repair、Pareto Top-K、AOT lowering、correctness validation 和 complete-step measurement。
F-1 草图见 `figures/drafts/F1_system_loop.svg`。

系统不把 candidate label 当作执行证据。每个进入比较的计划都必须记录 plan identity、effective
SAVE set、runtime adoption marker、FW/BW executable identity、fallback 状态和 multi-step
correctness 结果。

## 5 搜索、下发与测量

候选搜索使用 min-cut、block 和 greedy seeds 产生初解，再通过 peak live set 和 diagnosis hints
修复候选集合。由于静态 cost ranking 可能偏弱，最终选择依赖 Top-K 实测闭环。

测量协议区分 warmup、compile time、steady-state step time、CUDA Event phase timing 和同步
wall-clock。OOM、timeout、correctness failure、unsupported 和 fallback 都是结果，不从分母中
静默删除。
